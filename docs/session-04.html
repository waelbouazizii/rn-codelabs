Prérequis & objectifs

Objectif

Vos applications savent lire une base locale (séance 02) et une API REST (séance 03). Cette séance branche un backend complet sans écrire de serveur : Firebase. Vous construisez Shared Task Board, un tableau de tâches partagé : inscription et connexion par e-mail, tâches synchronisées en temps réel entre deux téléphones, et règles de sécurité qui empêchent de modifier les tâches des autres. Tout tourne dans Expo Go.

Avant la séance

Ouvrez Expo Go sur votre téléphone, installé depuis le store, et lisez la version de SDK qu'il prend en charge. Elle doit correspondre au SDK utilisé sur cette page : SDK 57, et à l'option --template default@sdk-57 de l'Étape 1. Sur iPhone, seule la version de l'App Store fonctionne : en cas d'écart, attendez la mise à jour de la page au lieu d'installer une autre version d'Expo Go. Vérifiez aussi que npx expo whoami et Expo Go affichent le même compte Expo. Enfin, ouvrez https://console.firebase.google.com sur le PC et retrouvez le projet Firebase créé en séance 00 : la connexion par e-mail et mot de passe doit être activée (Authentication) et une base Firestore doit exister (Firestore Database). Si vous travaillez en binôme, décidez avant l'atelier quel projet Firebase vous partagez.

À la fin de la séance, vous savez

  1. expliquer ce qu'apporte un backend as a service par rapport à l'API REST de la séance 03, et pourquoi seul le SDK JavaScript de Firebase fonctionne dans Expo Go ;
  2. initialiser Firebase avec des variables EXPO_PUBLIC_* et garder la session avec initializeAuth + getReactNativePersistence(AsyncStorage) ;
  3. construire une porte d'entrée dans le layout racine avec onAuthStateChanged, un Context et Stack.Protected ;
  4. lire et écrire dans Firestore (addDoc, updateDoc, deleteDoc, serverTimestamp, requêtes) et écouter en temps réel avec onSnapshot, désabonnement compris ;
  5. écrire, publier et tester des règles de sécurité : la configuration Web n'est pas un secret, les règles sont la sécurité.

Idées fausses visées par la séance : « l'apiKey Firebase est un secret à cacher », « une écriture Firestore n'apparaît qu'après la réponse du serveur » et « Expo Go exécute n'importe quel paquet npm ».

Où se place cette séance

Durée : 15 min.

Le découpage écran, hook, dépôt ne change pas. Ce qui change : la source de données pousse elle-même les changements vers l'application, et la sécurité ne vit plus dans un serveur que vous écrivez, mais dans des règles déclarées dans la console.

API REST maison ou backend as a service

Avec DummyJSON, quelqu'un a écrit un serveur : des routes, une base, un contrôle d'accès. Firebase fournit ces briques toutes faites (backend as a service) : un service d'authentification, une base de documents (Firestore) et un langage de règles. L'application parle directement à la base, sans route intermédiaire.

Question API REST maison (séance 03) Firebase (séance 04)
Code serveur à écrire Routes, contrôleurs, accès à la base Aucun : SDK client + règles
Authentification À coder (jeton, expiration, stockage) Service Authentication, session gérée par le SDK
Contrôle d'accès Dans le code du serveur Règles de sécurité, évaluées à chaque lecture et écriture
Temps réel À ajouter (WebSocket, sondage) Natif : onSnapshot pousse chaque changement
Requêtes Ce que le serveur expose Requêtes simples sur une collection (filtres, tri, limite), pas de jointure
Coût Hébergement du serveur Gratuit dans les quotas du plan Spark, puis à l'usage

Le plan gratuit (Spark) compte les opérations par jour et par projet : 50 000 lectures et 20 000 écritures. Chaque document reçu par un écouteur compte comme une lecture : un écouteur oublié qui se réabonne à chaque Fast Refresh consomme ce quota pour rien.

Quel SDK Firebase dans Expo Go ?

Il existe deux façons d'utiliser Firebase en React Native. Le paquet firebase est le SDK JavaScript, le même que sur le Web : du JavaScript pur, sans code natif. Les paquets @react-native-firebase/* enveloppent les SDK natifs Android et iOS : ils apportent du code natif, absent d'Expo Go, et demandent un build de développement. Ce cours utilise donc uniquement le SDK JavaScript.

La configuration Web d'un projet Firebase

Durée : 10 min.

La console Firebase fournit, pour chaque application Web enregistrée, un objet de six valeurs : apiKey, authDomain, projectId, storageBucket, messagingSenderId, appId. Elles désignent votre projet ; elles ne donnent aucun droit par elles-mêmes. On les place dans un fichier .env pour que chaque étudiant utilise son propre projet sans modifier le code.

  • Seules les variables dont le nom commence par EXPO_PUBLIC_ sont copiées dans le bundle ; les autres restent invisibles pour l'application.
  • La copie a lieu quand Metro construit le bundle : après une modification de .env, arrêtez npx expo start avec Ctrl+C et relancez-le.
  • .env n'est jamais commité : on ajoute la ligne .env au .gitignore et on commite un modèle .env.example aux valeurs vides.
  • Ne mettez jamais un vrai secret (clé d'administration, mot de passe) dans une variable EXPO_PUBLIC_ : toute personne qui possède l'application peut le lire.

La sécurité de vos données ne repose pas sur la configuration, qui est publique, mais sur les règles de sécurité de Firestore. Une base en mode test, ouverte à tous, est lisible et modifiable par n'importe qui qui connaît l'identifiant du projet.

Initialiser Firebase une seule fois

Le module src/lib/firebase.ts de l'Étape 1 crée l'application, le service d'authentification et la base. Les écrans ne l'importent jamais directement : seuls les fichiers de src/features le font.

Exemple à lire : fichier src/lib/firebase.ts (vous le créerez à l'Étape 1)

import AsyncStorage from '@react-native-async-storage/async-storage';
import { getApp, getApps, initializeApp } from 'firebase/app';
import { getAuth, initializeAuth, type Auth } from 'firebase/auth';
// @ts-expect-error TS2305: the React Native build of firebase/auth exports getReactNativePersistence, but its default type declarations do not list it.
import { getReactNativePersistence } from 'firebase/auth';
import { getFirestore } from 'firebase/firestore';

const firebaseConfig = {
  apiKey: process.env.EXPO_PUBLIC_FIREBASE_API_KEY,
  authDomain: process.env.EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN,
  projectId: process.env.EXPO_PUBLIC_FIREBASE_PROJECT_ID,
  storageBucket: process.env.EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET,
  messagingSenderId: process.env.EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID,
  appId: process.env.EXPO_PUBLIC_FIREBASE_APP_ID,
};

export const app = getApps().length ? getApp() : initializeApp(firebaseConfig);

let auth: Auth;
try {
  auth = initializeAuth(app, { persistence: getReactNativePersistence(AsyncStorage) });
} catch {
  auth = getAuth(app);
}
export { auth };
export const db = getFirestore(app);

À lire dans ce code :

  • getApps().length ? getApp() : initializeApp(firebaseConfig) : Fast Refresh peut réexécuter ce module ; on réutilise alors l'application existante au lieu d'en créer une seconde.
  • initializeAuth avec getReactNativePersistence(AsyncStorage) : la session est enregistrée sur le téléphone et survit au redémarrage. Avec getAuth seul, la session resterait en mémoire et l'utilisateur devrait se reconnecter à chaque lancement.
  • Le try/catch : un second appel à initializeAuth (par exemple après un Fast Refresh) lève une erreur ; on récupère alors l'instance déjà créée avec getAuth.
  • // @ts-expect-error : à l'exécution, Metro charge la version React Native de firebase/auth, qui exporte getReactNativePersistence ; mais les déclarations de types lues par TypeScript ne la listent pas, d'où l'erreur TS2305. C'est la seule exception du cours à la règle « pas de suppression d'erreur TypeScript ». Si une future version de Firebase corrige ses types, tsc signalera la directive inutile (TS2578) : il suffira de supprimer la ligne de commentaire.
  • getFirestore(app) : sur React Native, le cache de Firestore est en mémoire.

Un écouteur, une seule source de vérité

Durée : 20 min.

Firebase Authentication gère les comptes (createUserWithEmailAndPassword, signInWithEmailAndPassword, signOut) et garde la session. L'application ne stocke rien elle-même : elle s'abonne à onAuthStateChanged, qui appelle une fonction à chaque changement d'utilisateur, y compris au lancement, quand la session est restaurée depuis AsyncStorage.

Conséquence : signIn ne met pas à jour l'état React. Il appelle Firebase ; Firebase prévient l'écouteur ; l'écouteur met à jour le Context. Connexion, déconnexion, session restaurée ou expirée passent toutes par le même chemin.

Trois états, pas deux

Au lancement, la restauration de la session est asynchrone : au premier rendu, user vaut null même si quelqu'un est connecté. Le Context expose donc un second état, initializing, vrai jusqu'au premier appel de l'écouteur.

Expo Router exprime la porte dans le layout racine avec Stack.Protected : une route dont la garde est fausse n'est pas accessible, et Expo Router redirige vers la première route autorisée. Quand la garde change (connexion, déconnexion), la navigation suit d'elle-même : aucun router.replace à écrire.

Exemple à lire : fichier src/app/_layout.tsx (vous le créerez à l'Étape 2)

import { Stack } from 'expo-router';
import { ActivityIndicator, StyleSheet, View } from 'react-native';
import { AuthProvider, useAuth } from '@/features/auth/AuthContext';

function RootNavigator() {
  const { user, initializing } = useAuth();

  if (initializing) {
    return (
      <View style={styles.loading}>
        <ActivityIndicator size="large" />
      </View>
    );
  }

  return (
    <Stack>
      <Stack.Protected guard={user !== null}>
        <Stack.Screen name="index" options={{ title: 'Tableau partagé' }} />
      </Stack.Protected>
      <Stack.Protected guard={user === null}>
        <Stack.Screen name="sign-in" options={{ title: 'Connexion' }} />
      </Stack.Protected>
    </Stack>
  );
}

export default function RootLayout() {
  return (
    <AuthProvider>
      <RootNavigator />
    </AuthProvider>
  );
}

const styles = StyleSheet.create({
  loading: { flex: 1, alignItems: 'center', justifyContent: 'center', backgroundColor: '#ffffff' },
});

Dépendance au SDK : Stack.Protected existe depuis Expo Router 5 (SDK 53) et a été vérifié avec Expo Router 57.0.28 (SDK 57).

La restauration depuis AsyncStorage est asynchrone : au premier rendu, user vaut null. L'écouteur, branché dans un useEffect, ne répond qu'après ce premier rendu, comme un LaunchedEffect ou un initState. Seul initializing distingue « pas encore su » de « pas connecté ».

Collections et documents

Durée : 25 min.

Firestore range les données en collections de documents. Un document est un petit objet JSON (des champs typés : chaîne, nombre, booléen, horodatage) identifié par un identifiant unique. Il n'y a ni tables, ni schéma imposé, ni jointures : on conçoit les documents d'après les écrans qui les lisent.

Le tableau de l'atelier est une seule collection tasks. Chaque document porte title, done, ownerId (l'uid de la personne qui l'a créé), ownerEmail et createdAt.

Aide-mémoire, à consulter pendant les étapes : les fonctions Firestore de la séance

Fonction Rôle
collection(db, 'tasks') référence à une collection
doc(db, 'tasks', id) référence à un document
addDoc(collectionRef, data) crée un document avec un identifiant généré
updateDoc(docRef, { done: true }) modifie les champs indiqués, garde les autres
deleteDoc(docRef) supprime le document
serverTimestamp() valeur remplacée par l'heure du serveur à l'enregistrement
query(collectionRef, orderBy('createdAt', 'desc')) requête : filtres (where), tri (orderBy), limite (limit)
getDocs(query) lit une fois, comme un GET
onSnapshot(query, onNext, onError) écoute : rappel immédiat, puis à chaque changement ; renvoie la fonction de désabonnement

Lire une fois ou écouter

getDocs ressemble au fetch de la séance 03 : une réponse, puis plus rien. onSnapshot garde une connexion ouverte : Firestore rappelle la fonction avec la liste complète à jour à chaque ajout, modification ou suppression, quel que soit l'appareil qui l'a faite. Un écouteur vit donc aussi longtemps que l'écran qui l'affiche : on l'ouvre dans un useEffect et on renvoie sa fonction de désabonnement.

Exemple à lire : fichier src/features/tasks/tasksRepo.ts (vous le créerez à l'Étape 3)

import {
  addDoc,
  collection,
  deleteDoc,
  doc,
  onSnapshot,
  orderBy,
  query,
  serverTimestamp,
  updateDoc,
  type Timestamp,
  type Unsubscribe,
} from 'firebase/firestore';
import { db } from '@/lib/firebase';

export type Task = {
  id: string;
  title: string;
  done: boolean;
  ownerId: string;
  ownerEmail: string;
  createdAt: Timestamp | null;
  pending: boolean;
};

type TaskData = Omit<Task, 'id' | 'pending'>;

const tasksCollection = collection(db, 'tasks');

export const tasksRepo = {
  listen: (onChange: (tasks: Task[]) => void, onError: (error: Error) => void): Unsubscribe =>
    onSnapshot(
      query(tasksCollection, orderBy('createdAt', 'desc')),
      { includeMetadataChanges: true },
      (snapshot) => {
        onChange(
          snapshot.docs.map((d) => ({
            id: d.id,
            ...(d.data({ serverTimestamps: 'estimate' }) as TaskData),
            pending: d.metadata.hasPendingWrites,
          })),
        );
      },
      onError,
    ),
  add: (title: string, ownerId: string, ownerEmail: string) =>
    addDoc(tasksCollection, { title, done: false, ownerId, ownerEmail, createdAt: serverTimestamp() }),
  setDone: (id: string, done: boolean) => updateDoc(doc(db, 'tasks', id), { done }),
  remove: (id: string) => deleteDoc(doc(db, 'tasks', id)),
};

À lire dans ce code :

  • includeMetadataChanges: true : l'écouteur est aussi rappelé quand seul l'état « en attente » d'un document change, ce qui permet d'afficher puis d'effacer « en attente du serveur ».
  • d.data({ serverTimestamps: 'estimate' }) : tant que le serveur n'a pas fixé createdAt, Firestore fournit une estimation locale au lieu de null.
  • d.metadata.hasPendingWrites : vrai tant que l'écriture locale n'est pas confirmée par le serveur.
  • as TaskData : Firestore ne connaît pas vos types ; le dépôt est le seul endroit qui affirme la forme des documents.

L'écran voit l'écriture avant le serveur

Une écriture Firestore n'attend pas le réseau pour s'afficher. Firestore l'applique d'abord à son cache local et prévient tout de suite les écouteurs : c'est la compensation de latence. Le serveur évalue ensuite les règles de sécurité et confirme ou refuse.

La promesse de addDoc, updateDoc ou deleteDoc ne se résout qu'à la confirmation du serveur. Hors ligne, elle reste en attente : n'attendez pas sa résolution pour vider un formulaire ou fermer un écran.

Quiz éclair

Le téléphone est en mode avion, l'écran est abonné aux tâches avec onSnapshot. On appelle addDoc pour une nouvelle tâche. Que montre la liste ?

Firestore écrit d'abord dans son cache local et notifie les écouteurs : c'est la compensation de latence. L'écriture part vers le serveur dès que le réseau revient ; seule la promesse de addDoc attend cette confirmation.

Dans useTasks, l'effet appelle tasksRepo.listen mais ne renvoie pas la fonction de désabonnement. Que se passe-t-il à chaque fois que vous enregistrez un fichier et que Fast Refresh réexécute les effets ?

React n'arrête un abonnement que si l'effet renvoie une fonction de nettoyage, comme onDispose dans DisposableEffect. Sans elle, chaque réexécution de l'effet ajoute un écouteur, et chaque écouteur relit les documents.

Les règles sont la sécurité

Durée : 20 min.

La configuration Web est dans le bundle : n'importe qui peut l'extraire et appeler Firestore avec. Ce qui protège les données, ce sont les règles de sécurité, évaluées par les serveurs de Google pour chaque lecture et chaque écriture, écouteurs compris. Une base créée en mode production refuse tout ; c'est à vous d'ouvrir ce qui doit l'être.

Une règle allow s'applique à une opération (read, create, update, delete) quand sa condition est vraie. Si aucune règle ne s'applique, l'opération est refusée.

Aide-mémoire, à consulter pendant les étapes : les variables des règles

Expression Signification
request.auth l'utilisateur qui fait la requête ; null s'il n'est pas connecté
request.auth.uid son identifiant (le même que user.uid dans l'application)
resource.data le document tel qu'il est stocké, avant l'opération
request.resource.data le document tel qu'il serait après l'opération (création ou modification)
match /tasks/{taskId} la règle s'applique à chaque document de la collection tasks

Exemple à lire : fichier firestore.rules (vous le créerez à l'Étape 3)

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /tasks/{taskId} {
      allow read: if request.auth != null;
      allow create: if request.auth != null && request.resource.data.ownerId == request.auth.uid;
      allow update, delete: if request.auth != null && resource.data.ownerId == request.auth.uid;
    }
  }
}

À la création, le document n'existe pas encore : on vérifie request.resource.data.ownerId, la valeur envoyée. Pour modifier ou supprimer, on vérifie resource.data.ownerId, la valeur stockée : impossible de s'approprier la tâche d'un autre en envoyant son propre uid.

import {
  createUserWithEmailAndPassword,
  onAuthStateChanged,
  signInWithEmailAndPassword,
  signOut as firebaseSignOut,
  type User,
} from 'firebase/auth';
import { createContext, useContext, useEffect, useState, type ReactNode } from 'react';
import { auth } from '@/lib/firebase';

type AuthContextValue = {
  user: User | null;
  initializing: boolean;
  signIn: (email: string, password: string) => Promise<void>;
  signUp: (email: string, password: string) => Promise<void>;
  signOut: () => Promise<void>;
};

const AuthContext = createContext<AuthContextValue | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [initializing, setInitializing] = useState(true);

  useEffect(() => {
    const unsubscribe = onAuthStateChanged(auth, (nextUser) => {
      setUser(nextUser);
      setInitializing(false);
    });
    return unsubscribe;
  }, []);

  const signIn = async (email: string, password: string) => {
    await signInWithEmailAndPassword(auth, email, password);
  };

  const signUp = async (email: string, password: string) => {
    await createUserWithEmailAndPassword(auth, email, password);
  };

  const signOut = () => firebaseSignOut(auth);

  return (
    <AuthContext.Provider value={{ user, initializing, signIn, signUp, signOut }}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth(): AuthContextValue {
  const value = useContext(AuthContext);
  if (value === null) {
    throw new Error('useAuth must be used inside <AuthProvider>');
  }
  return value;
}

import {
  addDoc,
  collection,
  deleteDoc,
  doc,
  onSnapshot,
  orderBy,
  query,
  serverTimestamp,
  updateDoc,
  type Timestamp,
  type Unsubscribe,
} from 'firebase/firestore';
import { db } from '@/lib/firebase';

export type Task = {
  id: string;
  title: string;
  done: boolean;
  ownerId: string;
  ownerEmail: string;
  createdAt: Timestamp | null;
  pending: boolean;
};

type TaskData = Omit<Task, 'id' | 'pending'>;

const tasksCollection = collection(db, 'tasks');

export const tasksRepo = {
  listen: (onChange: (tasks: Task[]) => void, onError: (error: Error) => void): Unsubscribe =>
    onSnapshot(
      query(tasksCollection, orderBy('createdAt', 'desc')),
      { includeMetadataChanges: true },
      (snapshot) => {
        onChange(
          snapshot.docs.map((d) => ({
            id: d.id,
            ...(d.data({ serverTimestamps: 'estimate' }) as TaskData),
            pending: d.metadata.hasPendingWrites,
          })),
        );
      },
      onError,
    ),
  add: (title: string, ownerId: string, ownerEmail: string) =>
    addDoc(tasksCollection, { title, done: false, ownerId, ownerEmail, createdAt: serverTimestamp() }),
  setDone: (id: string, done: boolean) => updateDoc(doc(db, 'tasks', id), { done }),
  remove: (id: string) => deleteDoc(doc(db, 'tasks', id)),
};

export function firestoreErrorMessage(error: unknown): string {
  if (error instanceof FirebaseError) {
    if (error.code === 'permission-denied') {
      return 'Refusé par les règles de sécurité Firestore.';
    }
    if (error.code === 'unavailable') {

  }
  return 'Erreur inattendue. Réessayez.';

import { useEffect, useState } from 'react';
import { firestoreErrorMessage } from './firestoreErrors';
import { tasksRepo, type Task } from './tasksRepo';

export function useTasks() {
  const [tasks, setTasks] = useState<Task[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const unsubscribe = tasksRepo.listen(
      (next) => {
        setTasks(next);
        setError(null);
        setLoading(false);
      },
      (err) => {
        setError(firestoreErrorMessage(err));
        setLoading(false);
      },
    );
    return unsubscribe;
  }, []);

  return { tasks, loading, error };
}

import { useAuth } from '@/features/auth/AuthContext';
import { firestoreErrorMessage } from './firestoreErrors';
import { tasksRepo, type Task } from './tasksRepo';

export function useTasks() {
  const [tasks, setTasks] = useState<Task[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const unsubscribe = tasksRepo.listen(
      (next) => {
        setTasks(next);
        setError(null);
        setLoading(false);
      },
      (err) => {
        setError(firestoreErrorMessage(err));
        setLoading(false);
      },
    );
    return unsubscribe;
  }, []);

  return { tasks, loading, error };
}

export function useTaskActions() {
  const { user } = useAuth();
  const [actionError, setActionError] = useState<string | null>(null);

  const run = async (action: () => Promise<unknown>) => {
    setActionError(null);
    try {
      await action();
    } catch (err) {
      setActionError(firestoreErrorMessage(err));
    }
  };

  return {
    actionError,
    addTask: (title: string) =>
      run(async () => {
        if (user === null) return;
        await tasksRepo.add(title, user.uid, user.email ?? '');
      }),
    toggleTask: (task: Task) => run(() => tasksRepo.setDone(task.id, !task.done)),
    deleteTask: (task: Task) => run(() => tasksRepo.remove(task.id)),
  };
}

Fichier firestore.rules :

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /tasks/{taskId} {
      allow read: if request.auth != null;
      allow create: if request.auth != null
        && request.resource.data.ownerId == request.auth.uid
        && request.resource.data.title is string
        && request.resource.data.title.size() > 0
        && request.resource.data.title.size() <= 80;
      allow update: if request.auth != null
        && resource.data.ownerId == request.auth.uid
        && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['done']);
      allow delete: if request.auth != null && resource.data.ownerId == request.auth.uid;
    }
  }
}

À lire dans ces règles :

  • title is string et title.size() : la validation faite par les règles s'applique à tous les clients, même ceux qui ne passent pas par votre formulaire.
  • request.resource.data.diff(resource.data).affectedKeys().hasOnly(['done']) : la liste des champs modifiés ne doit contenir que done ; impossible de changer le titre ou le propriétaire d'une tâche.
