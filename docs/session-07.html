Session 07 - IAM2 React Native

Prérequis & objectifs

Objectif

Depuis six séances, chaque atelier a ajouté une source de données : SQLite (séance 02), une API REST (séance 03), Firestore (séance 04), un cache persistant et des notifications (séance 05), un appareil MQTT (séance 06). Cette dernière séance les range dans une seule architecture, prépare l'examen écrit, puis lance votre projet final. L'atelier ne construit pas de mini-application : vous créez le dossier project de votre dépôt, vous faites valider votre idée et vous livrez un premier écran qui traverse toutes les couches.

Avant la séance

[SDK] Dépendance au SDK : ouvrez Expo Go sur votre téléphone, installé depuis le store, et lisez la version de SDK qu'il prend en charge. Elle doit correspondre au SDK utilisé sur cette page : SDK 57, avec --template default@sdk-57. Sur iPhone, seule la version de l'App Store fonctionne : en cas d'écart, attendez la mise à jour de la page au lieu d'installer une autre version d'Expo Go. Vérifiez aussi que npx expo whoami et Expo Go affichent le même compte Expo.

À la fin de la séance, vous savez

  1. découper une application en couches : écran, hook, dépôt ou service, source de données ;
  2. choisir où placer un état : composant, Context, cache TanStack Query, stockage persistant, avec Zustand comme option pour un état client partagé ;
  3. comparer REST, SQLite, Firestore et MQTT selon la latence, le comportement hors ligne, la sécurité et le coût ;
  4. répondre à des questions de type examen sur les séances 01 à 06 ;
  5. expliquer les limites d'Expo Go et le chemin vers la production : development build, EAS Build, notifications distantes ;
  6. cadrer et lancer votre projet final : arborescence, modèle de données et première tranche verticale.

Idées fausses visées par la séance : « un écran peut interroger la base directement, c'est plus simple », « un Context ne relance que les composants concernés par le champ modifié », « Firestore garde un cache sur disque sur React Native » et « QoS 1 veut dire livré une seule fois ».

Objectif

Nommer les quatre couches d'une application, savoir quel fichier a le droit d'importer quoi, et retrouver ces couches dans Compose et Flutter.

Les quatre couches

Compose, Flutter et React Native

Couche Compose Flutter React Native
Écran Composable d'écran Widget de page Fichier de src/app
Logique d'écran ViewModel + StateFlow BLoC ou ChangeNotifier Hook personnalisé (custom hook)
Accès aux données Repository Repository Module repo ou service

Pourquoi ? Un écran qui ne connaît qu'un hook peut être relu et testé sans base ni réseau : il suffit de remplacer ce qui se trouve derrière le hook. Le même découpage permet de changer de source (SQLite vers REST, par exemple) en modifiant les couches basses, pendant que l'écran reste identique. Le défi de l'atelier en fait la démonstration.

Erreurs fréquentes : Un écran de src/app qui importe un module de src/db ou de firebase/firestore saute deux couches. Le code fonctionne, mais la requête est liée à cet écran : le deuxième écran la recopie, et changer de source oblige à réécrire l'interface.

Quiz éclair

Un écran appelle fetch directement dans un useEffect. Quel est le principal problème d'architecture ?

Le problème est le couplage, pas la syntaxe : le code compile et fetch fonctionne dans Expo Go. Mais l'écran connaît l'URL, le format de la réponse et la gestion des erreurs ; remplacer la source ou le tester sans réseau oblige à le réécrire. En plus, depuis la séance 03, les données serveur passent par TanStack Query.

Aide-mémoire, à consulter pendant les étapes : où placer l'état

Type d'état Où Outil Équivalent Compose/Flutter
UI locale (champ de saisie, bascule) Composant useState remember, setState
Partagé et rarement modifié (session, thème) Racine Context CompositionLocal, Provider

Pourquoi ? Quand la valeur d'un Context change, React relance le rendu de tous les composants qui le consomment, même ceux qui ne lisent qu'un champ resté identique. C'est sans effet visible pour une session ou un thème, qui changent rarement. Pour un filtre modifié à chaque frappe, un état local ou un store avec sélection fine convient mieux.

Erreurs fréquentes : Recopier une réponse d'API dans un useState ou un Context crée une deuxième copie à synchroniser à la main. Les données serveur restent dans le cache de requêtes ; les écrans s'y abonnent avec la même clé.

Zustand, en aperçu

[SDK] Dépendance au SDK : compatibilité de Zustand avec Expo Go sur le SDK 57 non vérifiée en salle. Les ateliers n'en ont pas besoin ; si vous le choisissez pour le projet, essayez-le sur votre téléphone avant d'en dépendre.

Quiz éclair

Une liste de produits vient d'une API et s'affiche dans trois écrans. Où placer cet état ?

C'est un état serveur : l'application n'en détient qu'une copie qui peut vieillir. Avec la même clé de requête, les trois écrans lisent le même cache, les requêtes simultanées sont dédoublonnées, et TanStack Query gère la fraîcheur, les erreurs et les nouvelles tentatives. Un useState ou un Context vous obligerait à réécrire tout cela.

Aide-mémoire, à consulter pendant les étapes : quatre sources de données

Critère REST + TanStack Query SQLite Firestore MQTT
Modèle Requête/réponse Relationnel local Base temps réel avec écouteurs Publication/abonnement
Latence Un aller-retour réseau ; immédiate quand le cache répond Très faible : aucun réseau Réseau ; chaque changement est poussé vers les écouteurs Réseau ; chaque message est poussé dès sa publication
Hors ligne Cache à persister (séance 05) Total Cache en mémoire seulement sur React Native, perdu au redémarrage Dernier état retenu seulement, reçu à la reconnexion ; dépend du broker
Sécurité Jeton Bearer gardé dans SecureStore Fichier local sur l'appareil Règles de sécurité Broker privé avec identifiants ; le préfixe de topics range, il ne protège pas
Coût et limites Dépend de l'API Aucun Quotas du plan Spark Broker gratuit limité
Cas d'usage Catalogue Dépenses personnelles Tableau partagé entre deux téléphones Télémétrie d'un ESP32

Pourquoi ? Aucune source ne gagne partout, et une même application en combine souvent plusieurs : un catalogue venu d'une API, un panier dans SQLite, des données partagées dans Firestore. Grâce aux couches du premier panneau, chaque source reste derrière son dépôt ou son service.

Erreurs fréquentes : « QoS 1 signifie livré une seule fois » est faux : QoS 1 garantit au moins une livraison, des doublons restent possibles. Le récepteur doit supporter de traiter deux fois le même message ; « exactement une fois » correspond à QoS 2.

Quiz éclair

Un ESP32 publie son statut en retained avec un LWT offline. L'application se connecte une heure plus tard et s'abonne. Que reçoit-elle ?

Un topic ne garde qu'un seul message retenu : le dernier publié avec le drapeau retain. Le broker l'envoie dès l'abonnement. Si l'appareil a disparu entre-temps et que son testament est retenu lui aussi, comme en séance 06, ce dernier message est offline. L'historique de l'heure écoulée n'est pas conservé.

2. Écrire une migration v1 vers v2

La table books existe en version 1 sur des téléphones qui contiennent déjà des données. Écrivez la migration vers la version 2 qui ajoute la colonne note TEXT sans perte de données, avec PRAGMA user_version.

Voir la réponse

Le bloc attendu est celui de version === 1, avec DATABASE_VERSION porté à 2. ALTER TABLE ajoute la colonne et conserve les lignes ; les anciennes ont note à NULL.

import type { SQLiteDatabase } from 'expo-sqlite';

const DATABASE_VERSION = 2;

export async function migrateDbIfNeeded(db: SQLiteDatabase): Promise<void> {
  const row = await db.getFirstAsync<{ user_version: number }>('PRAGMA user_version');
  let version = row?.user_version ?? 0;
  if (version >= DATABASE_VERSION) return;
  if (version === 0) {
    await db.execAsync(`
      PRAGMA journal_mode = 'wal';
      CREATE TABLE IF NOT EXISTS books (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        title TEXT NOT NULL,
        author TEXT NOT NULL,
        status TEXT NOT NULL,
        created_at INTEGER NOT NULL
      );
    `);
    version = 1;
  }
  if (version === 1) {
    await db.execAsync('ALTER TABLE books ADD COLUMN note TEXT;');
    version = 2;
  }
  await db.execAsync(`PRAGMA user_version = ${DATABASE_VERSION}`);
}

Une installation neuve passe par les deux blocs ; un téléphone en version 1 n'exécute que le second.

4. Trouver le bug 

import { collection, onSnapshot, orderBy, query } from 'firebase/firestore';
import { useEffect, useState } from 'react';
import { db } from '@/lib/firebase';

type Book = { id: string; title: string; author: string; status: 'todo' | 'reading' | 'done' };

export function useSharedBooks() {
  const [books, setBooks] = useState<Book[]>([]);

  useEffect(() => {
    const q = query(collection(db, 'books'), orderBy('createdAt', 'desc'));
    onSnapshot(q, (snap) => {
      setBooks(snap.docs.map((d) => ({ id: d.id, ...(d.data() as Omit<Book, 'id'>) })));
    });
  }, []);

  return books;
}

Ce hook affiche bien les livres. Où est le bug, et comment le corriger ?

Voir la réponse

L'effet n'a pas de fonction de nettoyage : l'écouteur onSnapshot survit au démontage du composant. Chaque nouveau montage en ajoute un, ce qui consomme des lectures sur le quota et de la mémoire. La correction renvoie la fonction de désabonnement :

import { collection, onSnapshot, orderBy, query } from 'firebase/firestore';
import { useEffect, useState } from 'react';
import { db } from '@/lib/firebase';

type Book = { id: string; title: string; author: string; status: 'todo' | 'reading' | 'done' };

export function useSharedBooks() {
  const [books, setBooks] = useState<Book[]>([]);

  useEffect(() => {
    const q = query(collection(db, 'books'), orderBy('createdAt', 'desc'));
    const unsubscribe = onSnapshot(q, (snap) => {
      setBooks(snap.docs.map((d) => ({ id: d.id, ...(d.data() as Omit<Book, 'id'>) })));
    });
    return unsubscribe;
  }, []);

  return books;
}

5. Une configuration incohérente

Une application configure staleTime à 30 secondes, gcTime à 1 heure et la persistance du cache avec un maxAge de 1 jour. Qu'est-ce qui ne va pas ?

Voir la réponse

gcTime doit être supérieur ou égal à maxAge, sinon le cache est supprimé de la mémoire avant la restauration prévue : la copie persistée perd ces données bien avant 1 jour. Il faut porter gcTime à 1 jour au moins. staleTime à 30 secondes ne pose pas de problème : il règle la fraîcheur, pas la durée de conservation.

6. Lire des règles Firestore 

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /books/{bookId} {
      allow read: if request.auth != null;
      allow create: if request.auth != null && request.resource.data.ownerId == request.auth.uid;
      allow update, delete: if request.auth != null && resource.data.ownerId == request.auth.uid;
    }
  }
}

Avec ces règles, qui peut supprimer un document de la collection books ?

Voir la réponse

Seul le propriétaire connecté : il faut request.auth != null et resource.data.ownerId == request.auth.uid, c'est-à-dire que l'ownerId stocké dans le document soit l'uid de la personne qui demande la suppression. Un autre utilisateur connecté peut lire le document, pas le supprimer.

7. MQTT : s'abonner après coup

Un appareil publie son topic status en retained avec un LWT offline. L'application s'abonne à ce topic 1 heure plus tard. Que reçoit-elle ?

Voir la réponse

Immédiatement le dernier message retenu du topic : online si c'est la dernière valeur publiée par l'appareil, ou offline si le broker a depuis publié son testament retenu. Elle ne reçoit pas les messages intermédiaires.

Quiz éclair

Sur React Native, l'utilisateur passe en mode avion, tue l'application puis la relance. Que voit-il des données Firestore (SDK JavaScript, configuration par défaut) ?

React Native n'a pas IndexedDB : le SDK JavaScript de Firestore ne garde qu'un cache en mémoire. Il disparaît avec le processus, qu'un écouteur ait été actif ou non. Pour relire ces données après un redémarrage hors ligne, il faut les copier soi-même sur le disque (SQLite, par exemple).

Objectif

Durée : 10 min.

Savoir ce qui oblige à quitter Expo Go, et situer les outils qui mènent à une application publiée. Cette partie est théorique : aucun atelier ne l'applique et aucune commande n'est à lancer.

Quand Expo Go ne suffit plus

Expo Go est une application déjà compilée : elle contient un ensemble fixe de modules natifs, et votre code JavaScript s'exécute à l'intérieur. Sortent donc d'Expo Go : les bibliothèques natives qu'il n'inclut pas, par exemple react-native-mmkv ou @react-native-firebase/* ; les notifications push distantes, qui demandent des jetons et les services FCM (Android) ou APNs (Apple) ; et plus généralement toute dépendance qui exige une configuration native.

Un development build est votre propre Expo Go, avec vos modules natifs : on garde le rechargement rapide, mais on installe son application au lieu d'Expo Go. EAS Build est la construction des binaires dans le cloud d'Expo, sans chaîne de compilation native sur votre PC. La soumission aux stores envoie ensuite ces binaires à Google Play et à l'App Store, avec leurs comptes développeur et leur examen. Les mises à jour OTA (over the air) livrent un nouveau code JavaScript et de nouvelles ressources à une application déjà installée ; un changement de code natif demande toujours une nouvelle construction.

Étape Ce que c'est Ce qui est possible Ce qui change pour le développeur
Expo Go Application prête à l'emploi, installée depuis le store Tout ce qu'incluent ses modules natifs ; notifications locales Rien à compiler : on scanne un QR code
Development build Votre propre application de développement Tout module natif et sa configuration, notifications distantes comprises Il faut reconstruire après un changement natif
EAS Build Service de construction des binaires dans le cloud Produire les builds de développement et de production Un compte Expo, une configuration de build et des identifiants de signature ; quotas selon l'offre
Store Google Play et App Store Distribuer au public ; mises à jour OTA ensuite pour le JavaScript Comptes développeur, fiches, examen avant publication et numéros de version

[SDK] Dépendance au SDK : le comportement exact des notifications distantes dans Expo Go est à vérifier avant le cours : il a changé entre versions du SDK et peut différer entre Android et iOS. Les ateliers n'utilisent que des notifications locales.

Quiz éclair

Pourquoi les notifications push distantes sont-elles exclues des ateliers ?

La limite est native, pas une question de vitesse ni d'offre : une notification distante passe par FCM ou APNs, configurés dans votre propre binaire. [SDK] Le comportement exact d'Expo Go sur ce point dépend de la version du SDK.

import type { SQLiteDatabase } from 'expo-sqlite';

const DATABASE_VERSION = 1;

export async function migrateDbIfNeeded(db: SQLiteDatabase): Promise<void> {
  const row = await db.getFirstAsync<{ user_version: number }>('PRAGMA user_version');
  let version = row?.user_version ?? 0;
  if (version >= DATABASE_VERSION) return;
  if (version === 0) {
    await db.execAsync(`
      PRAGMA journal_mode = 'wal';
      CREATE TABLE IF NOT EXISTS books (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        title TEXT NOT NULL,
        author TEXT NOT NULL,
        status TEXT NOT NULL,
        created_at INTEGER NOT NULL
      );
    `);
    version = 1;
  }
  await db.execAsync(`PRAGMA user_version = ${DATABASE_VERSION}`);
}

Fichier src/db/bookRepo.ts (nouveau) :

import type { SQLiteDatabase } from 'expo-sqlite';

export type BookStatus = 'todo' | 'reading' | 'done';
export type Book = { id: number; title: string; author: string; status: BookStatus; created_at: number };
export type NewBook = Pick<Book, 'title' | 'author' | 'status'>;

export const bookRepo = (db: SQLiteDatabase) => ({
  all: () => db.getAllAsync<Book>('SELECT * FROM books ORDER BY created_at DESC'),
  add: (b: NewBook) =>
    db.runAsync(
      'INSERT INTO books (title, author, status, created_at) VALUES (?, ?, ?, ?)',
      b.title,
      b.author,
      b.status,
      Date.now(),
    ),
  remove: (id: number) => db.runAsync('DELETE FROM books WHERE id = ?', id),
});

import { useSQLiteContext } from 'expo-sqlite';
import { useEffect, useState } from 'react';
import { bookRepo, type Book, type NewBook } from '@/db/bookRepo';

export function useBooks() {
  const db = useSQLiteContext();
  const [books, setBooks] = useState<Book[]>([]);

  useEffect(() => {
    let active = true;
    bookRepo(db)
      .all()
      .then((rows) => {
        if (active) setBooks(rows);
      });
    return () => {
      active = false;
    };
  }, [db]);

  async function add(book: NewBook) {
    const repo = bookRepo(db);
    await repo.add(book);
    setBooks(await repo.all());
  }

  async function remove(id: number) {
    const repo = bookRepo(db);
    await repo.remove(id);
    setBooks(await repo.all());
  }

  return { books, add, remove };
}

import type { Book } from '@/db/bookRepo';
import type { BookRepository } from '@/features/books/BookRepository';

export function createMemoryBookRepo(): BookRepository {
  let rows: Book[] = [];
  let nextId = 1;
  return {
    all: async () => [...rows],
    add: async (b) => {
      rows = [{ id: nextId++, created_at: Date.now(), ...b }, ...rows];
    },
    remove: async (id) => {
      rows = rows.filter((r) => r.id !== id);
    },
  };
}

À retenir

Pourquoi ? La frontière du dépôt est ce qui permet de remplacer SQLite par REST ou Firestore : tant qu'une implémentation respecte l'interface, ni le hook ni l'écran ne changent. Les fichiers de src/db importent ici le type BookRepository de src/features : c'est une inversion de dépendance, où l'implémentation obéit à un contrat fixé par la couche du dessus. import type disparaît à la compilation, donc aucun code d'exécution ne remonte.

Erreurs fréquentes : Créer le dépôt directement dans le corps du hook, sans useState, produit un nouvel objet à chaque rendu : l'effet qui dépend de repo peut alors se relancer sans fin, et la version mémoire perd ses données. Le React Compiler peut masquer ce défaut : ne comptez pas dessus.

Checklist d'évaluation

Cochez chaque point sur votre PC et votre téléphone avant de passer au livrable.

  • L'application s'ouvre dans Expo Go depuis npx expo start, lancé dans project.
  • npx tsc --noEmit ne signale aucune erreur, sans any.
  • Les dossiers src/features, src/db, src/lib et src/components existent.
  • La migration vers la version 1 utilise PRAGMA user_version.
  • Aucun écran de src/app ne contient de SQL ni d'import depuis @/db.
  • PROJECT.md est complet et marqué « validé ».
  • DATA-MODEL.md décrit la collection Firestore et le brouillon de règles.
  • Le README contient le diagramme Mermaid et la sortie d'expo-doctor.
  • Bonus (défi, facultatif) : l'interface du dépôt existe et le hook en dépend.

Objectif

Durée : 10 min.

Publier le lancement du projet : le dossier project avec le README, la capture docs/slice.png, un commit et le tag project-kickoff poussés sur GitHub. Ce n'est pas la remise finale : le tag project-submit sera demandé 10 jours après la séance.

Commandes

Vérifiez que project/docs/slice.png existe et que le README est complet. Le Terminal 2 est dans project : la première ligne revient à la racine du dépôt, la seconde doit répondre project/.env.

Terminal 2 — Bash et PowerShell (identique) :

cd ..
git check-ignore project/.env

Seulement si la commande a affiché project/.env : publiez et posez le tag.

Terminal 2 — Bash et PowerShell (identique) :

git add project
git commit -m "Project kickoff: scaffold, data model, first slice"
git push
git tag project-kickoff
git push origin project-kickoff

Résultat et vérification

  • Sur github.com, le dossier project montre src, PROJECT.md, DATA-MODEL.md, README.md, .env.example et docs/slice.png, mais ni node_modules ni .env.
  • La page du dossier project affiche le diagramme et la capture prise sur le téléphone.
  • Sur github.com, l'onglet des tags montre project-kickoff.

À retenir

Pourquoi ? Le tag project-kickoff fige le point de départ validé : vous pouvez toujours comparer votre travail à ce commit, ou y revenir. Pendant les 10 jours qui suivent, ajoutez une exigence à la fois, avec un commit pour chacune, en gardant l'application ouvrable dans Expo Go à tout moment.
