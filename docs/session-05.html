Prérequis & objectifs

Objectif

Vos applications lisent une base locale (séance 02), une API REST (séance 03) et Firestore en temps réel (séance 04). Mais coupez le réseau ou redémarrez l'application : le catalogue de la Mini-Shop disparaît, car le cache de TanStack Query vit en mémoire. Cette séance rend la Mini-Shop utilisable hors ligne. Vous construisez Offline-ready Shop : le catalogue et les fiches déjà consultées réapparaissent au redémarrage, une bannière signale l'absence de réseau, une commande passée hors ligne part au retour de la connexion, et un bouton « Rappelle-moi » programme une notification locale. Tout tourne dans Expo Go.

Avant la séance

Ouvrez Expo Go sur votre téléphone, installé depuis le store, et lisez la version de SDK qu'il prend en charge. Elle doit correspondre au SDK utilisé sur cette page : SDK 57, celui de votre s3-mini-shop, créé avec --template default@sdk-57. Sur iPhone, seule la version de l'App Store fonctionne : en cas d'écart, attendez la mise à jour de la page au lieu d'installer une autre version d'Expo Go. Vérifiez aussi que npx expo whoami et Expo Go affichent le même compte Expo. Enfin, lancez votre s3-mini-shop une dernière fois : le catalogue, la fiche produit, la connexion et le panier doivent fonctionner, car l'atelier part de ce code.

À la fin de la séance, vous savez

  1. définir hors ligne d'abord (offline-first), stale-while-revalidate et invalidation, et choisir le bon stockage pour chaque donnée ;
  2. expliquer pourquoi le SDK JavaScript de Firestore n'a qu'un cache en mémoire sur React Native ;
  3. persister le cache de TanStack Query avec PersistQueryClientProvider et un persisteur AsyncStorage, en reliant gcTime, maxAge et buster, et en excluant les données sensibles ;
  4. brancher onlineManager sur NetInfo et focusManager sur AppState, distinguer status et fetchStatus, et choisir networkMode pour une source locale ;
  5. expliquer ce que devient une mutation lancée hors ligne ;
  6. programmer une notification locale avec expo-notifications : handler, canal Android, permission, déclencheurs, annulation.

Idées fausses visées par la séance : « le cache de TanStack Query est déjà sur le disque », « gcTime et maxAge, c'est la même chose », « Firestore garde ses données sur le disque sur React Native » et « une requête SQLite n'a pas besoin du réseau, donc TanStack Query l'exécute toujours ».

Objectif

Durée : 15 min.

Situer le cache dans l'architecture et choisir le bon stockage pour chaque donnée.

Architecture

Trois mots à connaître

Hors ligne d'abord (offline-first)
L'application affiche d'abord ce qu'elle a déjà, puis met à jour quand le réseau répond. L'absence de réseau est un cas normal, pas une erreur.
Stale-while-revalidate
Montrer une donnée périmée pendant qu'on en redemande une fraîche. C'est déjà le comportement de TanStack Query avec staleTime (séance 03).
Invalidation
Déclarer qu'une donnée en cache n'est plus fiable, pour forcer un nouvel appel (invalidateQueries, séance 03). Au niveau du fichier persisté, c'est le rôle de maxAge et de buster (panneau suivant).

Aide-mémoire, à consulter pendant les étapes : quelle donnée, quel stockage

Donnée Stockage Survit au redémarrage Pourquoi
Catalogue et fiches produit cache de requêtes persisté dans AsyncStorage Oui, 24 h au plus Copie jetable d'une donnée du serveur : on peut toujours la redemander.
Panier SQLite (séance 03) Oui Donnée de l'utilisateur : la base locale est la source de vérité.
Jeton de connexion SecureStore (séance 03) Oui Secret : stockage chiffré.
Profil (/auth/me) cache de requêtes, en mémoire seulement Non Dépend du jeton et contient des données personnelles : pas de copie en clair dans AsyncStorage.
Tâches Firestore (séance 04) cache du SDK Firestore, en mémoire Non Voir le panneau suivant.

Pourquoi ? Le cache de TanStack Query est un objet JavaScript. Quand l'application redémarre, ou quand vous rechargez le code avec r, cet objet est recréé vide. staleTime décide quand redemander une donnée ; il ne dit rien de l'endroit où elle est gardée.

Quiz éclair

Dans la Mini-Shop de la séance 03, sans persisteur, vous parcourez le catalogue, puis l'application est complètement fermée. Vous la rouvrez sans réseau. Qu'affiche l'onglet Catalogue ?

Le QueryClient vit en mémoire : fermer l'application l'efface. staleTime ne règle que le moment où une donnée est redemandée. Pour retrouver le catalogue au redémarrage, il faut un persisteur, que vous ajoutez à l'Étape 2.

Objectif

Durée : 12 min.

Comprendre ce que le SDK JavaScript de Firestore garde hors ligne, et ce qu'il perd.

Deux caches, deux durées de vie

  • Sur le Web, Firestore peut garder son cache sur le disque du navigateur grâce à IndexedDB (option persistentLocalCache).
  • React Native n'a pas IndexedDB. Le SDK JavaScript de Firestore, le seul qui tourne dans Expo Go (séance 04), utilise donc un cache en mémoire.
  • Tant que l'application reste ouverte, ce cache suffit : onSnapshot continue d'afficher les documents déjà reçus, et une écriture hors ligne apparaît tout de suite avec l'état « en attente », comme à l'Étape 6 de la séance 04.
  • Si l'application est fermée hors ligne, ce cache et les écritures en attente disparaissent. Au redémarrage sans réseau, la liste reste vide.

Pourquoi ? Ce que vous aviez gratuitement avec Firebase en Kotlin ou en Flutter vient des SDK natifs. Dans Expo Go, seul le code JavaScript est chargé : l'application doit choisir elle-même ce qu'elle copie sur le disque. C'est exactement ce que fait cette séance pour l'API REST.

Quiz éclair

Une application installée utilise le SDK JavaScript de Firestore, comme le tableau de la séance 04. Hors ligne, l'utilisateur la ferme complètement, puis la rouvre, toujours hors ligne. Que montre la liste des tâches ?

Sur React Native, le SDK JavaScript de Firestore n'a pas IndexedDB : son cache, écritures en attente comprises, vit en mémoire. Il protège contre une coupure pendant l'utilisation, pas contre un redémarrage hors ligne.

import { PersistQueryClientProvider } from '@tanstack/react-query-persist-client';
import { Stack } from 'expo-router';
import { SQLiteProvider } from 'expo-sqlite';
import { migrateDbIfNeeded } from '@/db/migrations';
import { AuthProvider } from '@/features/auth/AuthContext';
import {
  CACHE_BUSTER,
  ONE_DAY,
  persister,
  queryClient,
  shouldPersistQuery,
} from '@/lib/queryClient';

export default function RootLayout() {
  return (
    <PersistQueryClientProvider
      client={queryClient}
      persistOptions={{
        persister,
        maxAge: ONE_DAY,
        buster: CACHE_BUSTER,
        dehydrateOptions: { shouldDehydrateQuery: shouldPersistQuery },
      }}
    >
      <SQLiteProvider databaseName="shop.db" onInit={migrateDbIfNeeded}>
        <AuthProvider>
          <Stack>
            <Stack.Screen name="(tabs)" options={{ headerShown: false }} />
            <Stack.Screen name="product/[id]" options={{ title: 'Produit' }} />
          </Stack>
        </AuthProvider>
      </SQLiteProvider>
    </PersistQueryClientProvider>
  );
}

Les quatre options de persistOptions :

  • persister : où écrire. Ici AsyncStorage, une clé « shop-query-cache ».
  • maxAge : âge maximal du fichier. Au-delà de 24 h, il est ignoré au démarrage.
  • buster : une étiquette de version. Si elle change, l'ancien fichier est ignoré. Changez-la quand la forme des données en cache change.
  • dehydrateOptions.shouldDehydrateQuery : choisir les requêtes écrites. La séance garde le choix par défaut (requêtes réussies) et exclut le profil et le panier.

Aide-mémoire, à consulter pendant les étapes : staleTime, gcTime, maxAge

Réglage Question à laquelle il répond Valeur dans la séance
staleTime Quand redemander une donnée au serveur ? 30 s (séance 03)
gcTime Quand oublier une requête que plus aucun écran n'utilise ? 24 h
maxAge Jusqu'à quel âge le fichier persisté est-il restauré ? 24 h

Attention : gcTime doit être au moins égal à maxAge. Le persisteur écrit ce qui est en mémoire : une requête oubliée après 5 minutes (valeur par défaut de gcTime) disparaît aussi du fichier, même si maxAge vaut 24 h.

Pourquoi ? AsyncStorage n'est pas chiffré. On y met des copies jetables de données publiques (le catalogue), jamais le jeton ni le profil. Le panier est déjà dans SQLite : le dupliquer créerait deux vérités.

Quiz éclair

Vous laissez gcTime à sa valeur par défaut (5 minutes) et réglez maxAge à 24 h. Vous ouvrez la fiche d'un produit, revenez au catalogue et continuez à naviguer 10 minutes. L'application est ensuite fermée et rouverte sans réseau. La fiche de ce produit est-elle restaurée ?

Le persisteur réécrit le fichier à partir du cache en mémoire. Quand gcTime supprime une requête inutilisée, la copie suivante ne la contient plus. maxAge ne fait qu'écarter un fichier trop vieux : d'où la règle gcTime au moins égal à maxAge.

Durée : 20 min.

Dire à TanStack Query quand le téléphone est hors ligne et quand l'application revient au premier plan, et savoir ce que devient une mutation lancée sans réseau.

Deux gestionnaires à brancher

  • onlineManager : sur React Native, TanStack Query ne connaît pas l'état du réseau et suppose qu'il est toujours disponible. On le branche sur NetInfo. Hors ligne, les requêtes ne partent pas et ne consomment pas leurs essais (retry) ; elles repartent au retour du réseau.
  • focusManager : sur le Web, TanStack Query redemande les données périmées quand l'onglet redevient visible. Sur le téléphone, l'équivalent est le retour de l'application au premier plan, signalé par AppState.

Aide-mémoire, à consulter pendant les étapes : status et fetchStatus

Champ Valeurs Question
status pending, success, error Ai-je une donnée ?
fetchStatus fetching, paused, idle Un appel est-il en cours, en pause ou terminé ?

Hors ligne, une requête jamais chargée a status pending et fetchStatus paused : l'écran doit afficher un message « indisponible hors ligne », pas un indicateur de chargement sans fin.

networkMode : qui a besoin du réseau ?

Valeur Comportement hors ligne Usage dans la séance
'online' (défaut) la requête ou la mutation se met en pause API DummyJSON
'always' elle s'exécute quand même SQLite (panier), notifications locales
'offlineFirst' un premier essai, puis la pause non utilisé ici

Erreurs fréquentes : Après l'Étape 3, une requête SQLite laissée en mode 'online' se fige hors ligne : le panier ne se met plus à jour et « Retirer » ne fait rien, sans aucune erreur. TanStack Query ne sait pas que la fonction appelée est locale ; c'est à vous de le dire avec networkMode: 'always'.

Mutations en pause

Une mutation lancée hors ligne en mode 'online' passe à isPaused, avec status pending. Elle part automatiquement au retour du réseau. Mais elle vit en mémoire : si l'application est fermée avant, elle est perdue. Rendre une mutation durable demande de la persister elle aussi, ce qui dépasse cette séance.

Quiz éclair

onlineManager est branché sur NetInfo, mais useRemoveFromCart n'a pas d'option networkMode. En mode avion, vous appuyez sur « Retirer » dans le panier SQLite. Que se passe-t-il ?

networkMode 'online' est la valeur par défaut, pour les requêtes comme pour les mutations. TanStack Query ne regarde pas ce que fait mutationFn : hors ligne, il met la mutation en pause, sans erreur. Pour une source locale, on choisit networkMode: 'always'.

Quatre réglages

  1. Le handler (setNotificationHandler) : décide de l'affichage quand l'application est au premier plan.
  2. Le canal Android : depuis Android 8, chaque notification appartient à un canal (nom, importance). Il doit exister avant la première notification. Une fois créé, seuls son nom et sa description changent.
  3. La permission : demandée une fois. Si l'utilisateur refuse, seuls les réglages du téléphone peuvent la rendre.

Quiz éclair

L'application est au premier plan quand un rappel programmé arrive. Son handler renvoie shouldShowBanner: false et shouldShowList: false. Que voit l'utilisateur ?

Au premier plan, le système demande au handler comment présenter la notification. Avec bannière et liste à false, rien n'est affiché ; la notification n'est pas mise de côté pour plus tard. En arrière-plan, le système l'affiche sans consulter le handler.

Code complet

Fichier src/lib/queryClient.ts :

import AsyncStorage from '@react-native-async-storage/async-storage';
import { createAsyncStoragePersister } from '@tanstack/query-async-storage-persister';
import { defaultShouldDehydrateQuery, QueryClient, type Query } from '@tanstack/react-query';

export const ONE_DAY = 1000 * 60 * 60 * 24;

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      gcTime: ONE_DAY,
      retry: 2,
    },
  },
});

export const persister = createAsyncStoragePersister({
  storage: AsyncStorage,
  key: 'shop-query-cache',
});

// Change this value when the shape of the cached data changes: the old cache is discarded.
export const CACHE_BUSTER = 's5-v1';

// 'me' depends on the token, 'cart' already lives in SQLite: neither goes to AsyncStorage.
const NOT_PERSISTED = ['me', 'cart'];

export function shouldPersistQuery(query: Query): boolean {
  return defaultShouldDehydrateQuery(query) && !NOT_PERSISTED.includes(String(query.queryKey[0]));
}

import { onlineManager } from '@tanstack/react-query';
import { useEffect, useState } from 'react';

// TanStack Query asks NetInfo whether the phone is online.
// isConnected is null while NetInfo does not know yet: we treat it as online.
export function connectOnlineManager(): void {
  onlineManager.setEventListener((setOnline) =>
    NetInfo.addEventListener((state) => {
      setOnline(state.isConnected !== false);
    }),
  );
}

export function useIsOnline(): boolean {
  const [isOnline, setIsOnline] = useState(onlineManager.isOnline());
  useEffect(() => onlineManager.subscribe(setIsOnline), []);
  return isOnline;
}

import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { useSQLiteContext } from 'expo-sqlite';
import { cartRepo, type NewCartItem } from '@/db/cartRepo';

const CART_KEY = ['cart'] as const;

export function useCart() {
  const db = useSQLiteContext();
  const query = useQuery({
    queryKey: CART_KEY,
    queryFn: () => cartRepo(db).all(),
    staleTime: Infinity,
    networkMode: 'always',
  });
  const items = query.data ?? [];
  const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  const count = items.reduce((sum, item) => sum + item.quantity, 0);
  return { items, total, count, isPending: query.isPending };
}

export function useAddToCart() {
  const db = useSQLiteContext();
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (item: NewCartItem) => cartRepo(db).add(item),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: CART_KEY }),
    networkMode: 'always',
  });
}

export function useRemoveFromCart() {
  const db = useSQLiteContext();
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (productId: number) => cartRepo(db).remove(productId),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: CART_KEY }),
    networkMode: 'always',
  });

import { useEffect, useState } from 'react';

export function useNow(intervalMs: number): number {
  const [now, setNow] = useState(() => Date.now());
  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), intervalMs);
    return () => clearInterval(id);
  }, [intervalMs]);
  return now;
}

import { useSQLiteContext } from 'expo-sqlite';
import { cartRepo, type CartItem, type NewCartItem } from '@/db/cartRepo';
import { api } from '@/lib/api';

const CART_KEY = ['cart'] as const;

export function useCart() {
  const db = useSQLiteContext();
  const query = useQuery({
    queryKey: CART_KEY,
    queryFn: () => cartRepo(db).all(),
    staleTime: Infinity,
    networkMode: 'always',
  });
  const items = query.data ?? [];
  const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  const count = items.reduce((sum, item) => sum + item.quantity, 0);
  return { items, total, count, isPending: query.isPending };
}

export function useAddToCart() {
  const db = useSQLiteContext();
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (item: NewCartItem) => cartRepo(db).add(item),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: CART_KEY }),
    networkMode: 'always',
  });
}

    onSuccess: () => queryClient.invalidateQueries({ queryKey: CART_KEY }),
    networkMode: 'always',

}

import * as Notifications from 'expo-notifications';

const CHANNEL_ID = 'reminders';

// Without a handler, iOS and Android decide how a notification is shown while the app is open.
export function configureNotifications(): void {
  Notifications.setNotificationHandler({
    handleNotification: async () => ({
      shouldShowBanner: true,
      shouldShowList: true,
      shouldPlaySound: false,
      shouldSetBadge: false,
    }),
  });
}

async function ensureReady(): Promise<boolean> {
  if (Platform.OS === 'android') {
    // The channel must exist before the first notification (Android 8+).
    await Notifications.setNotificationChannelAsync(CHANNEL_ID, {
      name: 'Rappels',
      importance: Notifications.AndroidImportance.HIGH,
    });
  }
  const current = await Notifications.getPermissionsAsync();
  if (current.granted) return true;
  const requested = await Notifications.requestPermissionsAsync();
  return requested.granted;
}

export async function scheduleReminderIn(
  title: string,
  body: string,
  seconds: number,
): Promise<string | null> {
  if (!(await ensureReady())) return null;
  return Notifications.scheduleNotificationAsync({
    content: { title, body },
    trigger: {
      type: Notifications.SchedulableTriggerInputTypes.TIME_INTERVAL,
      seconds,
      channelId: CHANNEL_ID,
    },
  });
}
